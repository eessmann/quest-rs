## Findings at review time

1. **P0 — candidate-derived support metadata could forge a certificate.** At review time `Polynomial::from_scalars` used the open candidate `PointBackend::compare` to compute `effective_support` (`polynomial.rs`, approximately 150–178). `evaluate_lifted` then used this cached metadata to trim/skip coefficients even when called by audited `evaluate_enclosure` and `jet_enclosure` (approximately 283–297). A custom f64 point backend claiming coefficient 1 equals zero, combined with a custom solver returning constant 1 for the sealed target zero, gives `support=None`; residual proof sees zero, while the frozen binary64 export is genuinely `[1]`. Export equality checking does not catch this because it checks the stored coefficient against the payload, not which coefficients proof evaluation consumed. Parent assigned generic-polynomial remediation and a direct test to the native owner, plus an end-to-end forgery regression to itself. Independent proof must inspect every represented coefficient or derive support solely from admitted enclosing arithmetic. The same generic constructor can be instantiated with `Complex64` and a lying open point backend; complex norm evaluation/pole checks (`norm.rs`, approximately 188/344) and complex analysis cached-support consumers must also recompute exact complex support before granting evidence. This extension was sent to both fix owners.
2. **P1 — next-candidate failure erased evidence for the retained previous candidate.** `exchange.rs:340` cleared `attempt.coverage` before `reference()` returned. If the next QR solve or work admission failed, the previous candidate/export remained but its successful critical-point cover disappeared. Parent owns the fix: clear coverage only when the new candidate is ready to publish, and retain prior candidate/evidence together otherwise.
3. **P2 — retry-history byte accounting omitted retained capacity/headers.** `remez.rs:624–627` counted history length rather than `Vec` capacity even though appending at approximately 580/590 may grow capacity geometrically. Candidate accounting used coefficient length without the actual `Arc<Vec>` header/capacity; exported `Arc` headers were omitted too. This understates retained bytes before computing the next attempt's allowance. Parent accepted and is fixing capacity-aware history accounting; native owner is adding actual polynomial heap accounting. These are required for a strict aggregate byte contract.
